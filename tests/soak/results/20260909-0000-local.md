(every timestamp and count below re-verified against the raw logs). Verdict: an
environment cascade, not a product defect. Two independent infrastructure failures
followed scenario (d)'s nacos container restart; spotter kept working correctly
throughout, and every "healed in never" outcome after ~00:40 traces to the nacos

### Product verdict with evidence

- **Atlas pushes: 2264 calls, zero failures.** No `fanout push to sink "atlas"`
  error line exists in app.log for this run; every `synced instance to the
  discovery center successfully` (2064 in the window) landed on the stand-in.
  Spotter never starved the Atlas leg.
- **Nacos failure count by period** (error lines against the nacos sink): 00:25–00:34
  ~2088 (EOF/timeout/refused during the JVM rebuild — expected); 00:40–00:55 ~2,163
  (HTTP 500 Could-not-find-leader, intermittent acceptance); 00:56–01:09 ~0 500s
  (client timeouts against a stalling API); 01:10–01:22 ~17,542 500s (leaderless,
  hard).
- **Retry queue: correctly isolated per-sink, never dropped.** Max pending 130
  (reached 01:10:14, held to run end); 334 five-second ticks observed with a
  non-empty queue (`unsync service worked count`), each retrying every entry;
  21,379 `retry trying to push instance failed again` lines — the queue kept
  working the whole outage. Queue entries keyed `(instance, sink)`: the atlas sink
  was never queued for, only nacos.
- **The "healed in never" outcomes of (c) 00:06:36, (a) 00:15:35 and (f) 00:45:59
  are the nacos-Raft outage, not the pipeline.** Each scenario's divergence is
  nacos-side state that only a nacos write can heal: (c)'s stale spike-app pod
  sets and the ecs `spike-app-inst-1001` instance (registered 00:04–00:33,
  stuck), (a)'s 10→5 pod scale-down pending deregistrations, (f)'s post-restart
  re-sync writes. They predate and postdate the outage with healthy heal
  behavior in between: scenario (b) healed in 2.025s (00:19:09) and (e) in
  1m55.864s post-consul-start (00:37:02) — both inside their 2m bound, both
  during nacos-healthy windows.

### Environment classification

- **nacos 2.1.0 (derby / Raft `naming_persistent_service_v2`) on ARM/rosetta
  colima**: the plan §9.2 risk "Nacos 2.1.0 JVM flaky on ARM/colima" (§8.2
  resource floor, §9.2 table) materializing specifically on the restart path —
  the known restart-pathology: `docker restart` brings the HTTP endpoints back
  (readiness 200, service list non-empty) while the embedded Raft group never
  completes leader re-election, so all writes fail with `Could not find leader`
  indefinitely. A read-only health gate cannot detect this; only a write probe
  can.
- **k3s single-node API server under 1h sustained churn + 100-replica scale**:
  TLS handshake timeouts / http2 connection loss from 00:56:47 onward — the
  plan §9.2 "k3s container weight" risk surfacing at load, on the same machine
  already running a degraded nacos JVM.
- Both are stack-level failures on the local colima host, not product defects:
  plan §8.2 risk materialization.
